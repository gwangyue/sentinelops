# 黄金演示脚本：系统"做出来是什么样子"的定义

> 这份文件同时是三样东西：3 分钟的演示脚本、端到端的验收标准、`make demo-check` 的规格说明（G6）。
> 每一步都写明**命令**、**屏幕上应该看到什么**，以及**机器检查什么**。机器检查只看结构和关系，不看具体数字，因为 LLM 的输出每次都会有所不同。

---

## 规则

1. M1 第一天就实现 `make demo-check`：先用回放模式加一个假的 LLM 跑通，所有检查项都能执行，即使大部分暂时不通过。
2. 每完成一个里程碑，打开对应步骤的检查。到 M3 结束时，第 1–8 步必须全部通过；到 M4 结束时，第 1–10 步必须全部通过；到 M5 结束时，第 1–11 步必须全部通过。
3. 检查只验证"契约和关系"，例如诊断引用的观测 ID 是否存在、审批哈希是否一致，**不验证具体数值**。
4. 演示时屏幕上显示的内容，以本文件为准；02 篇里的【示意】输出，都以这里为最终版本。

## 演示的 11 个步骤

| # | 步骤 | 命令 | 屏幕上应该看到 | 机器检查（`demo-check`） | 打开时机 |
|---|---|---|---|---|---|
| 1 | 集群健康，巡检不调用 LLM | `sentinel patrol es-target` | "健康，0 个问题，用时 N 秒" | 审计里有 `patrol.healthy`；这次巡检没有任何模型调用记录 | M1 |
| 2 | 注入故障 | `sentinel bench inject es.disk_watermark.single` | 故障已注入，等待症状出现 | 检测器 `es.unassigned_shards` 在 120 秒内触发（S2 实测，ADR-009） | M1 |
| 3 | 诊断：有证据、有排序 | `sentinel investigations show <inv>` | 最多 3 个假设，每个都有置信度和证据（观测 ID + 原文片段） | 诊断能通过 schema 校验；所有引用的观测 ID 都存在、都属于本次调查；原文片段是对应摘要的子串；H1 的根因标签和场景的真实答案一致（只在本步检查） | M1 |
| 4 | 上下文报告 | `sentinel investigations context <inv>` | 每一层用了多少 token、放了什么、删了什么、为什么删 | ContextBundle 能通过 schema 校验；L0 和异常事实没有被删除；各层 token 总数不超过预算 | M2 |
| 5 | 修复方案 | （第 3 步的输出里就有） | 动作、参数、预演结果、影响范围、回滚方法、验证条件、有效期 | 动作在白名单里；参数能通过 `params_schema` 校验；`plan_hash` 能由确定性代码重新计算出来 | M3 |
| 6 | 审批，然后执行、验证 | `sentinel approvals approve <apv> --as approver` | 已批准 → 执行 → 验证通过（集群恢复绿色） | 审计中依次出现 `approval.decided` → `action.executed` → `verify.passed`；执行器记录的 `plan_hash` 和审批时的一致；幂等键唯一 | M3 |
| 7 | 确认根因，写入记忆 | `sentinel investigations confirm <inv> --root-cause H1` | 已确认，已写入记忆 `mem_x` | 审计中有 `rootcause.confirmed` → `memory.written`；记忆的 `source_investigations` 包含本次调查 | M3 |
| 8 | 再次注入同类故障，记忆生效 | 重复第 2、3 步 | 相似事故 `mem_x` 出现在上下文中；步数比第一次少 | 第二次调查的 L5 包含 `mem_x`；H1 的 `from_memory` 包含 `mem_x`；**不检查步数**（随机性太大，步数的变化由评测来证明） | M3 |
| 9 | 收敛曲线和记忆增益 | `sentinel eval curve --pack es` · `sentinel eval ablation memory --streams dev` | 各版本的 top-1 及区间；记忆增益和伤害率及区间 | 曲线上的每个点都有对应的 AgentVersion 和数据集版本；消融结果包含增益、伤害率、区间 3 项 | M2（离线运行，不在实时演示里） |
| 10 | 治理周报和审计校验 | `sentinel report weekly` · `sentinel audit verify --since 1d` | 5 个数和"需要你决定的事"；哈希链完整 | 周报里的每个数字都能用 SQL 从审计表里重新算出来；`audit verify` 返回 0 | M4（`audit verify` 在 M3 打开） |
| 11 | 在飞书里审批（09 篇） | 飞书 dev 群里点审批卡片的「批准」 | 卡片标题带 `[kind-dev]`，内容和 `approvals show` 一致；点击后变成"已批准，执行中"，随后收到"验证通过"卡片 | 回放 + 假飞书：`approval.requested` 生成审批卡片；模拟点击之后审计依次出现 `approval.decided`（actor 是 `human:<名字>`，reason 以 `[feishu]` 开头）→ `action.executed` → `verify.passed`，并推送结果卡片；白名单外的点击被拒绝 | M5 |

## 演示时的讲法（3 分钟）

| 时间 | 讲什么 | 对应步骤 |
|---|---|---|
| 0:00–0:20 | 问题：运维 Agent 最难的不是"会不会诊断"，而是"可不可信" | — |
| 0:20–1:00 | 健康时不调用 LLM；注入故障；诊断里每个论断都有证据 | 1–3 |
| 1:00–1:40 | 上下文报告：分层、预算、删了什么。方案带预演和回滚；审批绑定哈希；独立执行器 | 4–6 |
| 1:40–2:20 | 确认根因之后才写入记忆；同类故障再次出现，记忆以"待验证的假设"形式生效 | 7–8 |
| 2:20–3:00 | 证据：收敛曲线、记忆增益和伤害率、和规则基线的对比；周报和审计校验 | 9–10 |

## 失败时的演示预案

| 情况 | 预案 |
|---|---|
| 现场注入的故障，症状迟迟不出现 | 改用回放模式演示第 2–8 步（同样的命令，加上 `--replay <录制编号>`） |
| 现场诊断出错 | 照实讲："这正是评测要解决的问题"，然后切到第 9 步，展示它在评测里属于哪一类失败 |
| 外网不通（Gemini 或 LangSmith 无法访问） | 用事先录好的演示录屏 |
