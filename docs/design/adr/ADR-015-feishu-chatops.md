# ADR-015 引入飞书 ChatOps 入口（推翻"交互只做 CLI""ChatOps 审批不做"）

- 状态：已接受（2026-11-20，人确认）
- 相关：00 篇 §5（不做清单），07 篇 §3、§4、§7，09 篇（新增），ADR-002（没有公网入口）

## 背景

00 §5 把"ChatOps 审批"放进了不做清单，交互只做 CLI，执行器保留对接 ChatOps 的接口。M4 结束之后，负责人提出新的需求：巡检异常和待审批推送到飞书；在飞书里发起巡检、注入和录制，结果再推回飞书。CLI 的问题是人得守在终端前，审批又有 30 分钟有效期，不在电脑前就只能看着它过期。

## 决策

1. 新增里程碑 M5，引入飞书作为 CLI 之外的第二个入口。设计见 09 篇。
2. **安全模型不变**：飞书只调用 CLI 背后的同一批函数；审批照样要经过"方案哈希 + 执行器重新校验"；按钮只带 `approval_id`。
3. **不改契约**：`ApprovalDecision.approver` 仍然是 `human:<名字>`，渠道记在 `reason` 的前缀 `[feishu]` 里；不新增审计事件类型。
4. **不改 Agent 行为**：推送读审计表，图的节点不改，不冻结新版本，不重新评测，上线版本仍然是 v41。（M5 实现时修订：Agent 行为确实没改、也没重新评测，但版本哈希包含整个 `src/`，chatops 的代码改动会让当前代码没有对应版本，真实巡检会被拒绝。所以冻结了一个"行为不变"的版本 v43（同 v42，只为代码哈希记账，不评测，上线版本仍是 v41），和 v38–v41 的先例一样。见 09 §9）
5. 风险上限可以配置（默认 medium）；`high_risk_enabled` 同时控制 high 风险审批和 `/freeze`；飞书不能解冻；不开放"测试"指令；bench 只在 dev 开放。
6. dev 和 prod 使用两个独立的飞书自建应用。
7. 接入方式用长连接，保持"没有公网入口"。

## 放弃的方案

| 方案 | 放弃原因 |
|---|---|
| 自然语言指令（LLM 解析意图） | 多出一条"LLM 决定触发写操作或注入"的路径，评测和安全都要重新论证 |
| 在图的节点里直接调用飞书 | 改变 Agent 行为，要重新冻结和评测；飞书故障会拖住调查 |
| HTTP 回调 + Ingress | 需要公网入口和证书，推翻 ADR-002 的网络边界；kind 上还要额外配隧道 |
| dev 和 prod 共用一个 bot | 长连接不广播（S7 实测），本地调试会消费掉线上的事件；`open_id` 按应用区分，白名单也没法共用 |
| 给 approver 加一个 `channel` 字段 | 是契约修改；目前用 `reason` 前缀就能区分渠道，等真的需要统计时再改 |

## 后果

- 00 §5：把"ChatOps 审批"和"交互只做 CLI"改为 M5 范围内的飞书入口。
- 07 篇的威胁模型增加 T13–T16（写在 09 §8）。
- 新依赖 `lark-oapi`（飞书官方 SDK）。
- 新的技术验证 S7：在实现之前确认长连接、卡片回传、多客户端投递和回调时限。如果卡片回传不能走长连接，第 7 条要重新讨论（会改变网络边界）。
