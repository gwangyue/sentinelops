## B. 五条硬边界（违反任意一条，都要回到设计层面讨论）

- [x] **LLM 只在中间**：检测、上下文组装、执行、验证都是确定性代码；LLM 只负责诊断和选择动作（00 篇 P1）
- [x] **只有执行器能写**：执行器是独立进程、独立命名空间、独立凭证、没有外网出口；诊断 Agent 只有只读权限（ADR-005）
- [x] **审批不经过 LLM**：审批绑定方案哈希，有效期 30 分钟；执行器自己去 Postgres 读取审批记录，执行前再做一次前置检查（02 篇 §3.4）
- [x] **记忆只写人确认过的根因**（05 篇 §3.1）
- [x] **依赖方向**：专家包只依赖 `contracts` 和 `sdk`；`core` 不 import 具体的专家包；`exec` 不依赖 `core`（01 篇 §2）

## C. 契约要点（03 篇，只列关键的设计）

- [x] **证据链**：诊断里的每个论断都必须引用观测记录 ID，可以附原文片段；这样证据支持率可以用规则直接检查
- [x] **AgentVersion** = 提示词、模型（含参数）、工具描述、上下文策略、记忆策略、专家包版本、代码 commit 的哈希；每条评测结果都必须带上它
- [x] **动作规格**声明风险等级、参数 schema、前置条件、预演、回滚、验证条件、影响范围上限；执行器只按声明执行
- [x] **评测用例**的真实答案包括：根因标签、可接受的动作、禁止的动作、必须引用的工具、关键事实、是否应该升级
- [x] **事故记忆**支持合并（`occurrences`）和"易混淆"标记（`confused_with`）

## D. 指标与决策规则（06 篇）

- [x] **唯一的主指标**：top-1 准确率（根因标签比对，规则计算）
- [x] **安全底线**：不安全提议数必须等于 0
- [x] **决定能不能上线的指标全部用规则计算**；评审模型只用于失败归类
- [x] **统计**：按场景聚类的配对 bootstrap，95% 区间；下界 > 0 才算提升
- [x] **接受检测能力的上限**：开发集约 16 个场景时，能稳定检测到 0.15 以上的提升，0.10 大约一半一半（本机模拟实测）→ 每个版本只做一个大改动
- [x] **取舍规则**（§7.2）：主指标显著提升，并且费用没有超过上限 → 上线；主指标无法判断，但成本显著下降 → 上线；其他情况 → 不上线，记为一次"无效改动"
- [x] **三种笨基线**：多数类、纯规则、上下文完美
- [x] **保留测试集**：每个里程碑最多跑 1 次；用满 4 次就重建
