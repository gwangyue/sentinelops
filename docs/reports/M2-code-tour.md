# M2 代码导览

> 按 `docs/design/templates/code-tour.md` 生成。M1 的导览（`M1-code-tour.md`）走的是"巡检 → 诊断 → 报告"这条主线；本篇只讲 M2 在这条线上**新加的站**，加上评测这一侧的三站。30 分钟读完。

## 1. 路线图

```
sentinel patrol / eval run
   │
   ▼
detect ──▶ context 节点（investigation.py:148）
             │  ① L3 变更：现在 vs 注入前快照（changes.py）
             │  ② L5 记忆：指纹 → 三路召回 → 精排 → 阈值（memory/）     ← 默认关闭
             │  ③ 组装 + 预算 + 降级（build.py:91）
             ▼
         diagnose（Deep Agent）── ④ L2 压缩中间件（compaction.py:64）
             ▼
         RunScore ── ⑤ 失败标签（failures.py:42）
             ▼
 ⑥ 事故流运行器（stream.py:118）：模拟"人确认" → 写记忆 → 反馈
 ⑦ eval clusters / eval curve：失败分组、收敛曲线
```

## 2. 逐站讲解

### ① L3 变更层

| 项 | 内容 |
|---|---|
| 位置 | `core/context/changes.py:59` `diff`、`:77` `collect_changes`；调用方 `core/graph/investigation.py:287` `_changes` |
| 人话 | 把"现在的集群设置、节点列表、索引模板"和"上一次的快照"逐项比较，列出变了什么。回放时，"上一次"就是录制里注入故障之前的快照 |
| 输入 / 输出 | 输入：快照工具的原始输出（Observation）；输出：`Change` 列表（core 内部结构，不属于契约） |
| 关键概念 | 结构化 diff（字典按键比较；带 name 的列表按 name 对齐，这样节点顺序变了不算变化） |
| 为什么这样设计 | 04 §3.4；"最近改了什么"是运维排障的第一个问题。做成通用比较，不需要每个专家包各写一份 |
| 可能出错的地方 | 第一次巡检没有快照时，L3 是空的，也不会说明原因（`TODO(edge)`）；ILM 读不了（403），不在比较范围里 |
| 面试可能被问 | 问：为什么 L3 能让步数下降？答：节点类故障，L3 里直接写着"节点列表少了 data-2"，Agent 不用再自己调一次 `nodes_info` 去发现 |

### ② L5 记忆检索

| 项 | 内容 |
|---|---|
| 位置 | `core/memory/fingerprint.py:40` `build`；`retrieve.py:41` `retrieve`；`provider.py:16` `StoreMemoryProvider` |
| 人话 | 把这次的症状变成一组"指纹词"（哪个检测器报警、哪些事实异常、涉及什么类型的对象、最近改了什么），然后分三路去找历史事故：按指纹词找、按文字找、按向量找。三路结果合并后重新打分，低于 0.55 分的丢掉 |
| 输入 / 输出 | 输入：Finding、FactSheet、Change；输出：`MemoryHit`（L5 渲染用）；存储的是 `MemoryRecord`（03 §6.4） |
| 关键概念 | RRF（倒数排名融合：每一路里排第 r 名，就得 1/(k+r) 分，几路加起来）；加权 Jaccard（两组指纹词的重合比例，检测器的词权重最高） |
| 为什么这样设计 | 05 §3.2–3.3。精排时 RRF 特征改用 k=1（`retrieve.py:31`）：k=60 时分数几乎是平的，无关记忆也能过阈值 |
| 可能出错的地方 | **精度只有 0.32**：ES 的几种故障都会触发 `det:es.unassigned_shards` 和 `cluster.status:yellow`，指纹重合度很高。ES 9 读文档时默认不返回向量，读出来改了再写回会把向量写成空数组（已修复，`store.py` 的模块说明里有记录） |
| 面试可能被问 | 问：为什么记忆以"假设"而不是"结论"的形式呈现？答：精度 0.32 时，如果以结论的形式呈现，模型很可能照抄；以假设的形式呈现，M-E1 的伤害是 0 |

### ③ 组装、预算、降级

| 项 | 内容 |
|---|---|
| 位置 | `core/context/build.py:91` `build_context`；`:66` `_fit_layer`；`:76` `_degrade` |
| 人话 | 每一层先按自己的预算放条目，总量超出时按"知识 → 变更 → 记忆 → 次要事实"的顺序删，每删一条都记下原因。被管系统的文字一律包在 `<untrusted>` 标签里，并做转义 |
| 输入 / 输出 | 输出 `ContextBundle`（03 §4.5）：每个条目放了没有、为什么没放 |
| 关键概念 | 不可删的条目：问题事件、异常的事实、记忆的第一条 |
| 为什么这样设计 | 04 §3.7–3.8；E1 的原始数据模式也在这里（`raw` 参数），默认关闭 |
| 可能出错的地方 | 单条异常事实本身就超出预算时，仍然保留，预算会被突破（`TODO(edge)`，上下文报告里能看到） |
| 面试可能被问 | 问：E1 里原始数据步数更少，为什么不上线？答：3 节点集群的原始 JSON 不截断也放得下；集群一大就会被截断，这个结果推广不到真实规模 |

### ④ L2 压缩

| 项 | 内容 |
|---|---|
| 位置 | `core/diagnosis/compaction.py:64` `L2Compaction`（Deep Agent 的中间件），`:70` `wrap_model_call`；压缩规则在 `:41` `compact` |
| 人话 | 诊断过程中工具输出累积太多时（达到 `L2_max × trigger_ratio`），把旧的工具结果压成"工具名 + 第一行 + 观测 ID"，最近 3 条保留原样 |
| 输入 / 输出 | 输入：每次调用模型之前的消息列表（其中的 `ToolMessage`）；输出：压缩后的消息列表（只改发给模型的消息，不改 Agent 状态）。压缩记录 `CompactionRecord` 写进 `diagnosis.completed` 审计的 payload（04 实现说明：`ContextItem` 没有 L2，加就是改契约） |
| 关键概念 | **中间件**（LangChain 在每次调用模型前后插入的钩子：`wrap_model_call` 拿到请求、可以改写消息再交给模型）；**L2**（诊断过程中按需下钻拉取的上下文，不在预组装的包里） |
| 为什么这样设计 | 04 §3.11（G3）。保留观测 ID，压缩之后证据链也不会断；不用框架自带的摘要中间件，因为它不知道观测 ID 是证据链的关键，可能把 ID 摘掉 |
| 可能出错的地方 | 当前场景的 L2 远低于触发线，实际不会触发，所以只有单元测试证明它是对的；模型调工具时通常不写文字小结，压缩用的是摘要的第一行（确定性规则），第一行信息不够时模型要用 `/obs/<id>.json` 找回原文 |
| 面试可能被问 | 问：压缩会不会让证据检查失败？答：不会。压缩只改发给模型的消息，观测记录完整保留；压缩后的那一行仍然带观测 ID，模型引用 ID 时证据检查照常能找到原文 |

### ⑤ 失败标签

| 项 | 内容 |
|---|---|
| 位置 | `eval/failures.py:42` `rule_tags`；由 `eval/scorers.py` 的 `score` 在评分时调用；评审模型在 `:106` `judge_tags`、`:159` `apply_judge` |
| 人话 | 06 §6.1 那张表的直译：一次运行如果录制没覆盖、上下文缺了关键事实、没引用必查工具……就打上相应的标签。答对的运行也可能有标签 |
| 输入 / 输出 | 输入：`RunScore`（03 §6.3）和这次运行的输出（诊断、上下文包、升级原因）、用例的真实答案 `ExampleOutputs`；输出：`RunScore.failure_tags`。评审结果另存 `.judge.jsonl`，评审要看的诊断过程另存 `.runs.jsonl` |
| 关键概念 | **规则优先、评审补充**（06 §6.1：能用确定性规则判断的先用规则，评审模型 Pro 档只在"规则说不清为什么错"时调用）；**缓存评审结果**（重复执行 `eval clusters` 不重复计费，分组也不会因为评审的随机性而变） |
| 为什么这样设计 | 06 §6.1–6.2：失败归类是为了回答"下一步该改什么"，规则标签可复现、零成本；评审标签只用于归类，不参与上线决策 |
| 可能出错的地方 | `context_recall` 是按 ` key=` 这个格式查找的，换成原始 JSON 后会全部误判成 `retrieval_miss`（E1 时遇到过）；`missed_required_tool` 在答对的运行上也会出现（M2 的 dev 上 12/72 次），它说的是"证据不完整"，不是"答错" |
| 面试可能被问 | 问：为什么不让评审模型给所有失败打标签？答：评审有随机性、要花钱，而且它判断的是语义问题；"录制没覆盖""关键事实被预算删了"这类问题规则就能确定，交给模型反而不可复现 |

### ⑥ 事故流运行器

| 项 | 内容 |
|---|---|
| 位置 | `eval/stream.py:118` `run_stream_set`；`:213` `_one`；流的生成 `:54` `make_streams` |
| 人话 | 2 条流 × 3 次重复，一共 6 个任务并行；每个任务内部按顺序跑 12 个用例。每个用例跑完，用真实答案假装"人确认了根因"，写成记忆、更新反馈，给后面的用例用 |
| 输入 / 输出 | 输入：`datasets/streams/es.yaml`（固定种子打乱的用例顺序）、`EvalExample`、`StreamDeps`（运行、评分、建记忆索引的函数）；输出：`RunScore`（含 `memory_hit`）和记忆侧的 `MemoryRow`（L5 里出现了哪些记忆、有没有伤害），分别存 `.jsonl` 和 `.memory.jsonl` |
| 关键概念 | `memory_hit`（这条流前面出现过同一个根因时，相关记忆有没有进入 L5）；伤害（top-1 来自记忆、并且是错的）；**每条流一个临时记忆索引**（`mem-eval-<id>`，用完删掉，流与流之间互不影响） |
| 为什么这样设计 | 05 §4.2；evaluate() 是并发、无状态的，事故流必须有状态；流的顺序在看结果之前生成并提交，避免"按结果挑顺序" |
| 可能出错的地方 | 模拟确认用的是真实答案，比现实乐观；"来自记忆"靠模型自己填的 `from_memory`。这两条在 05 里都写明了；临时索引在任务异常退出时也要删（`finally` 里删） |
| 面试可能被问 | 问：为什么流内要按顺序、流与流之间可以并行？答：流内后面的用例要用前面写进记忆的结果，顺序就是实验条件；不同流、不同重复各有自己的记忆索引，没有共享状态 |

### ⑦ 失败分组和收敛曲线

| 项 | 内容 |
|---|---|
| 位置 | `eval/failures.py:129` `clusters`、`:142` `next_step`；`eval/curve.py:56` `points`、`:76` `render`；取舍记录在 `datasets/version_decisions.yaml` |
| 人话 | 把带标签的运行按"标签组合"分组，给出最该先处理的标签；把每个版本的 top1 和区间画成一张图，没上线的版本画成空心点 |
| 输入 / 输出 | 分组：输入 `RunScore` 列表，输出 `Cluster`（标签组合、运行次数、用例数、样例）；曲线：输入 `var/eval/` 的结果文件、版本 note、取舍记录，输出 `Point` 列表和 PNG |
| 关键概念 | **标签组合**（06 §6.2 第一版的分组方式：同一组标签算一类）；**按场景聚类的区间**（每个点的 95% 区间也按场景重采样，和比较用的口径一致）；**空心点**（06 §8：无效改动不从图上删除） |
| 为什么这样设计 | 06 §6.2、§8；取舍结论放在单独的 yaml 里，而不是从版本 note 推断：取舍是在评测之后才做的，结论一般写在下一个版本的 note 里，复用的版本没有 note |
| 可能出错的地方 | 版本的取舍结论要手动写进 yaml；漏写的话，没上线的版本会被画成实心点；数据集标签变了要画竖线，否则跳变分不清是数据集变了还是 Agent 变了 |
| 面试可能被问 | 问：为什么无效改动也要画在图上？答：只画上线的版本，曲线会显得"每次都在进步"；把无效改动留在图上，读者才知道试过什么、哪些没用，曲线才可信 |

## 4. 自测题

<details><summary>题 1：为什么 dev top1 已经是 1.00，还要跑 heldout？</summary>

答案：dev 是反复调过的，可能"调到了考题上"；heldout 只在里程碑跑，用来检查有没有过拟合。这次 heldout 也是 1.00，说明没有过拟合，但也说明这批场景太简单了。
</details>

<details><summary>题 2：M-E1 的命中率 0.93，为什么步数没有下降？</summary>

答案：不用记忆时 Agent 平均不到 3 步就答对了，没有可以省的东西；而且精度只有 0.32，多出来的不相关记忆还会多占 token。
</details>

<details><summary>题 3：v27 改回事实卡片之后，为什么没有出现新版本，而是复用了 v26？</summary>

答案：版本的哈希由组件（代码、配置、模型、提示词）算出。改回去之后，组件和 v26 完全相同，所以哈希相同，系统复用了 v26。
</details>

<details><summary>题 4：失败标签 `missed_required_tool` 在答对的运行上出现，说明了什么？</summary>

答案：根因判断对了，但证据没有引用场景规定必须查的工具（例如节点类故障要引用 `cluster_health`）。这是"答对了，但理由不完整"，下一个提示词版本可以针对这一点。
</details>

<details><summary>题 5：E1 满足 06 §7.2 第 4 条，为什么可以不照搬？</summary>

答案：规则的前提是"实验环境有代表性、测量指标有效"。E1 的环境是 3 节点集群（原始 JSON 不截断也装得下），召回率指标在原始数据模式下也失效了，所以由人决定不上线，并在 06 §7.2 里写明了原因。
</details>
