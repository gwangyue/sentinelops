## 0. 一句话总结

**M2 的东西都做出来了，也都实测过：17 个故障场景、上下文分层、记忆服务、事故流、失败归类、收敛曲线。但结论很朴素：现在的场景对 Agent 来说太简单了，dev 和 heldout 都是全对。4 个实验里只有"变更层"上线（它让 Agent 少查约 0.5 次），知识层、记忆、原始数据都没有显著效果。可以进入 M3；M3 之后要先做更难的场景，后面的实验才测得出差别。**

## 8. 风险和下一步

人话结论：最大的风险是场景太简单，后面的实验测不出差别；另外 M2 收尾时有几个固定动作漏了（独立审阅事后补做，漂移检查和工时没做）。

- **最担心的：场景太简单**。主指标到顶之后，后面所有的上下文、记忆实验都只能看步数和费用，而且区间很宽。M3 不受影响（M3 要证明的是"安全地执行修复"，不是"诊断得更准"），但 M3 之后、M4 之前，建议先做一轮更难的场景：性能类故障、更大的集群（让 E1 的结论可以推广）、多个干扰项。
- **记忆的精度 0.32**：ES 的几种故障指纹高度重叠。不处理的话，L5 一打开就会多花 token。M-E3（把阈值调到 0.7）可以直接针对这个问题，成本约 1.8 美元。
- **证据不完整**：答对了，但没有引用必查工具（dev 12/72 次）。可能和 L3 有关，L3 直接给出了变化，Agent 就不去查了。下一个提示词版本可以针对这一点。
- M3 开始前要先处理的：D10 需要你创建 `.claude/contracts.unlock`（新增 `ActionProposal`、`ScenarioSpec.remediation`，已经在计划里确认过）。

- **08 §6.6 的固定动作有两项没做**（事后核对发现，按你的决定留作缺口）：模型漂移检查（G2：用当前数据集重跑 M1 的上线版本 v7），以及 08 §8 的实际工时。独立审阅是事后补做的，结论见文末。

## 术语表

| 术语 | 白话解释 |
|---|---|
| dev / heldout | 开发集和保留测试集。开发集可以反复用来调；保留测试集只在里程碑跑，防止"调到考题上" |
| top1 | 排第一的根因猜对的比例 |
| 按场景聚类的 bootstrap | 把同一种故障的几次录制当成一组来重新抽样，避免把彼此相关的结果当作独立样本，区间算得过窄 |
| 区间 | 95% 置信区间：下界 > 0 才算显著提升，上界 < 0 才算显著退步 |
| 06 §7.2 第 4、5 条 | 第 4 条："主指标看不出差别，但更便宜或步数更少"就上线；第 5 条："什么都看不出差别"就记为无效改动 |
| L1 / L3 / L4 / L5 | 上下文的层：事实卡片 / 最近的配置变更 / runbook 知识 / 相似的历史事故 |
| 事故流 | 按时间排好的一串故障，前面的确认结果写成记忆，给后面的用 |
| 命中率 / 精度 / 伤害率 | 该出现的记忆出现了没有 / 出现的记忆里有多少是对的 / 记忆把答案带错的比例 |
| 失败标签 | 用确定性规则判断"为什么错"（或者"哪里还不够好"），例如 missed_required_tool = 没有引用必查工具的观测 |
| 评审模型 | 另一个更强的模型，只在规则说不清时给失败归类，不参与上线决定 |
| 收敛曲线 | 每个版本的分数连成一条线：实心点 = 上线，空心点 = 无效改动，菱形 = heldout |
| replay（回放） | 用录好的工具输出代替真实集群，同一个故障可以反复评测 |
